# 环境问题档案（已结案：非环境问题）

> **2026-08-27 结案**：本档案记录的"Electron DevTools CDP 命令分发失效"是**诊断脚本 bug 造成的误判**，
> 应用与系统环境从头到尾都正常。保留本文供后续参考，避免重蹈覆辙。

## 1. 真实根因（一句话）

**CDP 测试脚本在 WebSocket 101 握手完成之前就发送了命令帧**——Chromium 的 DevTools 会**静默丢弃**
握手完成前到达的帧，脚本永远收不到响应 → 误报"连接正常但无响应"。

## 2. 误判过程（教训）

- 2026-08-26 ~19:35：一次内联脚本偶然时序正确，CDP 成功（当时没意识到时序依赖）。
- ~20:45 起改用文件版脚本（`cdp-check.js`）：connect() 回调即 send → 命令先于握手 → 全部"无响应"。
- 此后多轮误判：回退代码、全新 profile、--disable-gpu、最小空应用、Electron 28（Chromium 120）
  对照、系统重启——**全部"仍死"**（因为它们绕不开同一个脚本 bug）。甚至误导性地排除了
  "代码/GPU/profile/SAC/版本/重启"，全部是假阴性。
- 2026-08-27 决定性一刻：raw-dump 脚本（握手后才发命令、原样打印字节）收到
  `{"id":1,"result":{"result":{"type":"number","value":2}}}` → 服务端秒回 → 定位到客户端时序。

## 3. 修复与工具

- **规则：任何 CDP 客户端必须在收到 101 之后才发第一条命令**（命令入队，握手后 flush）。
- 工作区现保留两个可用工具：
  - `cdp-check.js <port>`：连通性 + 1+1 评估
  - `cdp-eval.js <port> <js>`：通用页面评估（awaitPromise）
- 验证示例：`node cdp-eval.js 9421 '...js...'` → 渲染层状态/配置读取全部正常。

## 4. 真实存在的次生现象（与 CDP 无关）

- 幽灵 LISTENING 端口（9411/9412 残留、甚至 PID 0）：`taskkill //F` 强杀 Electron 进程树后的
  Windows 套接层残留，重启自愈；后续避免强杀，改用应用自身退出或 `Stop-Process` 优雅结束。
- 桌宠窗口会被同为置顶的 Clash Verge 面板遮挡（应用间置顶层级正常现象）。
- 无独立 Chrome/部分外网受限（GitHub 二进制下载被拦，可走 npmmirror 镜像）。

## 5. 影响复盘

- 应用本体与所有此前代码改动均正常（行走/语音/PSD/并发锁等验证均为日志级或真机 curl，有效）。
- "腿型微调"验证当时改用 PrintWindow+vision 闭环（§14-追加76），结论仍有效。
- 误判期间产出的其他结论（如"渲染进程反复重载"）需以日志为准复核——本轮 CDP 复验渲染层正常。
